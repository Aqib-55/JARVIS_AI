**Target Runtime:** Ollama (`http://localhost:11434`)
**Target Local Model:** `qwen3.5:4b`
**Host Environment:** Windows, Python 3.13 (.venv), VS Code

## 1. Executive Summary

This audit assesses the technical feasibility, architectural readiness, and migration path for integrating a local AI runtime (**Ollama** running **`qwen3.5:4b`**) into the existing JARVIS AI task-execution assistant, replacing or complementing the existing Google Gemini cloud integration.

### Key Audit Findings:
1. **Ollama Service & Model Verified:** Ollama v0.40.17 is active locally on `http://localhost:11434` with `qwen3.5:4b` (4.2B parameters, Q4_K_M quantization, 262k context window) verified and loaded.
2. **Native Tool Calling Confirmed:** Live probing confirmed that `qwen3.5:4b` under Ollama supports **true native tool/function calling** via `/api/chat` using standard OpenAI-compatible tool schemas, not simulated text-based JSON.
3. **Architectural Decoupling:** JARVIS's existing provider abstraction (`BaseProvider` in `providers/base.py` and factory in `providers/factory.py`) cleanly isolates model interactions from agent planning, tool execution, memory, permissions, and voice subsystems.
4. **Validation Test Passed:** A Python validation suite (`test_qwen_code.py`) verifying mathematical accuracy and type enforcement on code generated by Qwen passed all 7 standard tests and 3 invalid-input test cases.

## 2. Existing Project Architecture Overview

JARVIS AI is organized into decoupled layers:

```

└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐

       │              │              │             │
┌──────▼──────┐┌──────▼──────┐┌──────▼─────┐┌──────▼─────┐
│  AI Model   ││ Task Plan   ││ Safety &   ││ Persistent │
│  Provider   ││ & Execution ││ Permission ││ Memory     │
│             ││             ││            ││            │

└─────────────┘└──────┬──────┘└────────────┘└────────────┘
                      │
               ┌──────▼──────┐
               │Tool Registry│
               │ (26 Tools)  │
               └─────────────┘
```

### Core Subsystems:
- **`main.py`**: Entry point, logging configuration, provider instantiation via factory, tool registration, CLI boot.
- **`config/settings.py`**: Central typed settings loaded from `.env` via `python-dotenv`.
- **`providers/base.py`**: Abstract interface (`BaseProvider`, `FunctionCall`, `FunctionResponse`, `ModelResponse`, `Message`).
- **`providers/gemini.py`**: Cloud provider using `google-genai` SDK v3.x.
- **`core/agent.py`**: Multi-turn agent loop (up to 6 autonomous turns) coordinating planner, executor, permissions, memory, and model.
- **`core/planner.py`**: Multi-step dependency DAG resolution (`depends_on`), cycle detection, step lifecycle.
- **`core/executor.py`**: Step executor with retries, timeout delegation, tool schema validation, and emergency stop halt.
- **`core/permissions.py`**: 4-tier security model (L0 Read-Only, L1 Low Risk, L2 Moderate Risk, L3 High Risk), directory allowlists, path traversal blocking, emergency stop.
- **`tools/registry.py`**: Categorized registry holding 26 registered tools with timeout-guarded execution.
- **`memory/database.py` & `memory/memory_manager.py`**: SQLite Schema v2 with WAL mode storing conversation history, task DAGs, tool executions, facts, preferences, and usage metrics.
- **`voice/`**: Modular STT (SpeechRecognition / Faster-Whisper) and TTS (pyttsx3 / Edge TTS) with Push-to-Talk and Continuous listening modes.

## 3. Gemini Integration Deep-Dive (Current Baseline)

| Item | Gemini Implementation (`providers/gemini.py`) |
| :--- | :--- |
| **1. Message Reception** | `_build_contents()` maps `Message` objects into `google.genai.types.Content(role="user"\|"model", parts=[Part(text=...)])`. |
| **2. System Instructions** | Configured via `types.GenerateContentConfig(system_instruction=...)`. Augmented dynamically per turn in `agent.py` with retrieved long-term facts/preferences. |
| **3. Conversation History** | Active session sliding window in `core/conversation.py` (limited by `MAX_CONVERSATION_HISTORY`), backed durably in SQLite `messages` table. |
| **4. Tool Declarations** | `ToolRegistry.get_declarations()` outputs standard JSON schema; `_build_tools()` wraps each in `types.FunctionDeclaration` inside `types.Tool(function_declarations=...)`. |
| **5. Tool Call Parsing** | Extracted from `response.function_calls` into `providers.base.FunctionCall(name=..., args=dict(args))`. |
| **6. Tool Result Return** | `send_function_results()` appends model turn (`function_call`) followed by user turn (`function_response`), re-invoking `generate_content()`. |
| **7. Errors & Timeouts** | Transient 503/429 handled via exponential backoff (`_generate_with_retry()`). Exceptions sanitized with API key redaction (`[REDACTED_API_KEY]`). Tool timeouts enforced in `ToolRegistry.execute()`. |
| **8. Tool Call Limits** | Guarded by `JarvisAgent._max_autonomous_turns` (default 6 turns) and `TaskExecutor._max_tool_calls` (default 10 steps per plan). |
| **9. Safety Gates** | Level 3 tools require user approval callback; path validation blocks outside workspace; emergency stop halts turn immediately. |
| **10. Provider Selection** | `settings.ACTIVE_PROVIDER` read from `.env`, queried through `providers/factory.py:get_provider()`. |

## 4. Ollama Local Runtime & `qwen3.5:4b` Audit Findings

Live probing of `http://localhost:11434` with model `qwen3.5:4b` revealed the following exact behaviors:

### 4.1 Native Tool Calling Format
Ollama accepts tool declarations in OpenAI-compatible function schema:
```json
{
  "model": "qwen3.5:4b",
  "messages": [{"role": "user", "content": "..."}],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "tool_name",
        "description": "Tool description",
        "parameters": {
          "type": "object",
          "properties": {...},
          "required": [...]
        }
      }
    }
  ],
  "stream": false
}
```

### 4.2 Model Response with Tool Call
When `qwen3.5:4b` decides to invoke a tool, Ollama returns:
```json
{
  "model": "qwen3.5:4b",
  "message": {
    "role": "assistant",
    "content": "",
    "thinking": "Internal reasoning trace...",
    "tool_calls": [
      {
        "id": "call_xxxxxx",
        "function": {
          "name": "get_datetime",
          "arguments": {}
        }
      }
    ]
  },
  "done": true
}
```
*Note on Thinking Tokens:* `qwen3.5:4b` populates a `"thinking"` attribute in the message. In the provider response parser, `thinking` must not be confused with or injected into `content` so the CLI/Voice output remains clean.

### 4.3 Sending Tool Results Back
Ollama expects tool results in the message history with role `"tool"`:
```json
[
  {"role": "user", "content": "What is the date today?"},
  {
    "role": "assistant",
    "content": "",
    "tool_calls": [
      {"id": "call_xxxxxx", "function": {"name": "get_datetime", "arguments": {}}}
    ]
  },
  {
    "role": "tool",
    "tool_call_id": "call_xxxxxx",
    "content": "{\"datetime\": \"Monday, November 23, 2026\"}"
  }
]
```
The model then continues the generation and produces the final synthesized response.

## 5. Compatibility Analysis & Potential Challenges

| Area | Challenge | Mitigation Strategy |
| :--- | :--- | :--- |
| **Tool Schema Alignment** | `ToolDefinition.to_declaration()` currently returns `{name, description, parameters}`. Ollama expects `{type: "function", function: {name, description, parameters}}`. | The Ollama provider wrapper will simply wrap declarations inside `{"type": "function", "function": decl}`. Zero changes required in `tools/`! |
| **Thinking Mode Handling** | `qwen3.5:4b` outputs chain-of-thought in `message.thinking` and `content=""` when generating tool calls. | Provider will check `message.get("content")` and ignore `thinking` for final speech/CLI output, or expose it optionally under `debug` logging. |
| **Inference Latency** | Local 4.2B model running on local hardware requires 1.5s–4s per turn compared to cloud streaming. | Add connection timeout (60s) in HTTP client; provide user feedback ("Thinking...") before tool execution starts. |
| **Connection Availability** | Ollama might not be running or might crash if RAM/VRAM is exhausted. | Implement robust health-check in `connect()` pinging `http://localhost:11434/api/tags` and graceful error messaging advising user to launch Ollama. |
| **Multi-turn Context Length** | While `qwen3.5:4b` supports up to 262k context, local VRAM usage scales with active context. | Keep conversation history window bounded by `MAX_CONVERSATION_HISTORY` (20 turns) as currently implemented. |

## 7. Security & Safety Evaluation

1. **Zero Secret Leakage:** Local Ollama requires no API keys, eliminating risk of token leakage in source code or network logs.
2. **Local Privacy:** Full prompt text, user documents, and workspace file contents remain entirely on the local computer without traversing cloud networks.
3. **Preserved Permission Gates:** All tool executions remain strictly guarded by JARVIS's 4-tier security model (`core/permissions.py`), path traversal guards, and interactive user approvals for Level 3 actions regardless of which model provider requests them.
